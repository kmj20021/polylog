# Polylog 5분 발표 — 실제 대사 (comment.md)

> `index.html`의 **실제 슬라이드 8장 순서**에 맞춘 **말할 대사**입니다.
> 5분 = 말하기 4:25 + 데모 0:30(슬라이드 2에서 카드 클릭 재생) = 4:55 (버퍼 5초).
> 표기: 【N p】 화면 전환 · 〔동작〕 무대 지시 · ⏱ 누적 시간.
> **쉬운 말로 풀어 쓴 대본** — 어려운 용어는 한 번 말하고 바로 풀어 설명합니다. **[1]·[4]는 안 보고 암기**(Cat1 감점 방지).
>
> 🎬 **데모는 따로 없습니다.** 슬라이드 2의 4개 카드 제목(▶)을 누르면 그 기능 영상이 재생됩니다(`demo-schedule/recommend/menu/receipt.mp4`). 문제를 말하면서 곧바로 해당 영상을 보여 줍니다.
>
> ✅ 실제 코드 기준: 메뉴는 **구글 렌즈에 맡김**(앱이 직접 안 함), 영수증만 **Bedrock 비전으로 글자 인식**, 로그인은 **구글 토큰 검증(tokeninfo)**, Lambda는 **배포 7종(앱이 쓰는 건 6종, fn-menu는 안 씀)**.

## [3] 아키텍처 — 1:05 ⏱2:40 ★핵심
【3p 아키텍처 다이어그램】 〔다이어그램 클릭하면 확대〕

> "그럼 이게 **어떻게 돌아가는지** 보겠습니다.
> 네 기능 모두 **똑같은 한 줄 흐름**을 탑니다.
> 앱에서 버튼을 누르면 → **API Gateway**가 어디로 갈지 길을 안내하고(요청 받는 문) → 그 일을 맡은 **Lambda 함수**가 받아서 → 필요한 **AI나 외부 서비스**를 부르고 → 결과를 **DynamoDB나 S3**에 저장합니다.
>
> 기술을 왜 이렇게 골랐는지 흐름 따라 말씀드리면 —
> • 앱은 **Flutter** 하나로 만들었습니다. 코드 한 벌로 빨리 만들 수 있어 3주 프로젝트에 딱 맞습니다(ADR-003).
> • 서버는 **API Gateway + Lambda 7종**입니다. **평소엔 켜진 서버가 한 대도 없고**, 누가 쓸 때만 잠깐 켜져서 그만큼만 돈을 냅니다. 그래서 **한 달에 2~3달러**면 됩니다(ADR-001).
> • 로그인은 **구글 로그인**입니다. 구글이 준 신분증(ID 토큰)이 진짜인지 `fn-authorizer`가 **구글에 직접 물어봐서 확인**합니다. 우리 서버는 따로 기억할 게 없습니다(tokeninfo, ADR-007).
> • AI는 **Bedrock의 Claude 하나로 통일**했습니다. 장소 추천·일정 대화는 물론, **영수증 글자 읽기까지 한 번의 호출**로 끝냅니다(InvokeModel). 메뉴 번역만은 직접 안 하고 **구글 렌즈에 맡겼습니다**(이유는 다음 장에서).
> • 저장은 **DynamoDB**입니다. 여행 번호(trip_id)로 묶고 **시간을 정렬 기준으로** 둬서, 일정과 지출이 **알아서 시간순으로 정렬**됩니다(ADR-014/015). 사진 원본은 **S3**에 둡니다.
>
> 성능과 비용은 세 가지로 잡았습니다.
> ① **가벼운 Haiku 모델 + 프롬프트를 짧게** 써서 빠르고 쌉니다 ② **정렬은 저장 구조로 해결**해 따로 비용이 안 듭니다 ③ **평소 서버가 0대**라 고정비가 없습니다.
> 구조는 — 앱은 **기능별 폴더**(recommend·menu·receipt·schedule), 백엔드는 **기능마다 Lambda를 따로** 둬서 하나가 고장 나도 나머지는 멀쩡합니다."

> **📊 채점 (★ Cat1·Cat3 동시 — 가장 점수 큰 구간)**
> - ☑ **(Cat1) 적용 기술**: Flutter · API Gateway · Lambda 7종 · Bedrock(Claude) · DynamoDB · S3 빠짐없이
> - ☑ **(Cat1) 어떻게 구현**: "앱→API Gateway→Lambda→AI/외부→DynamoDB·S3" 한 줄 흐름
> - ☑ **(Cat3) 안 읽고 설명 + 이해**: 다이어그램 보며 "왜 이 구조인지"
> - ☑ **(Cat3) 성능 최적화 3가지**: Haiku+짧은 프롬프트 / 정렬 구조 / 서버 0대 — **반드시 셋 다**
> - ☑ **(Cat2 대비) 앱 구조**: 기능별 폴더 + 기능별 Lambda 분리
> ⚠️ "메뉴는 구글 렌즈" 빼먹으면 다음 장과 모순

## [4] ADR 4번복 — 0:50 ⏱3:30 ★핵심
【4p 결정을 번복한 4가지 표】 〔표 클릭하면 확대〕 〔대본 안 보고〕

> "여기까지 매끄럽지 않았습니다. **결정을 네 번 뒤집었고**, 전부 기록(ADR)에 남겼습니다.
>
> ① **로그인**: 처음엔 Cognito를 쓰려 했는데, 저희 공용 계정에선 권한이 막혀 있었습니다. 그래서 **구글 토큰을 직접 확인하는 방식**으로 돌아갔습니다(ADR-007). — *막히면 돌아간다.*
> ② **메뉴 번역**: 처음엔 사진을 AI 비전으로 읽어 번역까지 앱이 다 하려 했습니다. 그런데 **작은 모델 한 번에 읽기·번역·추천을 다 시키니 품질이 들쭉날쭉**했습니다. 그래서 카메라 번역을 잘하는 **구글 렌즈에 맡겼더니** 안정적이었습니다(ADR-016/018). — *직접 만드는 것보다 검증된 도구가 나을 때도 있다.* (영수증은 글자가 정해져 있어 Bedrock 비전 유지)
> ③ **사진 전송**: CloudFront(CDN)를 쓰려다, **PoC엔 과한 투자**고 영수증은 개인정보라 **만료되는 서명 주소(Presigned URL)**로 충분해서 뺐습니다(ADR-008). — *필요 이상으로 안 만든다.*
> ④ **일정 기능 분리**: 30초 걸리는 무거운 대화형 일정 짜기가, 가벼운 일정 저장 기능까지 느리게 만들었습니다. 그래서 **`fn-planner`를 따로 떼어내** 서로 영향 안 주게 했습니다(ADR-017). — *느린 건 따로 격리한다.*
>
> 이렇게 **모든 결정의 이유와 대안을 ADR로 기록**해 뒀습니다."

> **📊 채점 (★ Cat3 시행착오 + Cat2 질의응답 대비)**
> - ☑ **(Cat3) 개발자 관점 시행착오**: "네 번 뒤집음" — 문제→판단 구조
> - ☑ **(Cat2) ADR 번호 3개 이상**: 007·008·016/018·017 (번호를 입으로)
> - 번복 키워드: ① 막혀서 우회 ② 검증된 도구 ③ 과투자 회피 ④ 느린 것 격리
> ⚠️ **번호 안 부르면** "기록 기준 정확" 점수 약화 / **이유 빼면** 단순 변경으로 보임

## [8] (백업) 기술 채택 근거 — 질문 올 때만
【8p 기술 채택 근거 표】 〔질의응답에서 "왜 이 기술?" 질문 시 펼침〕

> 📌 9개 영역(컴퓨팅·DB·AI·장소·클라이언트·인증·미디어·리전·배포) + 기각한 대안 + ADR 번호가 표에 있습니다.

1. **왜 Cognito 말고 구글 로그인?** 공용 계정에서 Cognito가 막혀, 구글 토큰을 `fn-authorizer`가 **구글에 물어 확인**하는 방식으로 우회(ADR-007).
2. **Bedrock 리전?** 서비스는 서울인데 **Bedrock만 us-east-1**(서울에 없어서, ~200ms). 짧은 프롬프트로 상쇄(ADR-009).
3. **왜 DynamoDB?** 여행 단위 단순 접근 + 쓴 만큼 과금이 PoC에 맞음. **trip_id + 시각 정렬**로 정렬 비용 0(ADR-002/014/015).
4. **메뉴는 왜 직접 안 하고 구글 렌즈?** 작은 모델 한 번에 읽기·번역·추천을 다 시키면 품질 불안정 → 카메라 번역 전문인 렌즈에 위임. 영수증은 정형이라 Bedrock 비전 유지(ADR-016/018).
5. **월 비용?** 무료티어 ~$2~3, 종료 후 $10~15.
